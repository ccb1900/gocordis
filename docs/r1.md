### P1-01：Server Static 的路径参数实际上不支持多级目录

确定的功能缺陷

涉及：

* `extensions/server/server.go`

* `extensions/server/static/static.go`

Static 注册的路由是：

```go
c.Route + "/{path...}"
```

它希望捕获完整的相对文件路径，例如：

```text
/static/css/app.css
/static/js/app.js
/static/images/logo.png
```

但是当前 Router 的 `compilePattern()` 将 `{path...}` 当成普通单段参数处理。

`matchPath()` 又要求请求路径段数必须与路由段数完全相同。

因此：

```text
/static/app.css
```

可能匹配。

但：

```text
/static/css/app.css
```

无法匹配。

这意味着 Static 扩展虽然存在，但最常见的静态资源目录结构无法正常工作。

解决方案：

Router 应明确支持 catch-all 参数：

* `{id}`：匹配单个路径段。

* `{path...}`：匹配剩余全部路径段。

* catch-all 必须是最后一个参数。

* 明确空路径是否允许。

* 路径解码与 `..` 处理必须在路由和文件系统边界共同保证安全。

建议补充：

```text
/static/a.css
/static/css/a.css
/static/css/theme/dark.css
/static/
```

以及编码路径、路径穿越测试。

这是本轮最明确、应优先修复的功能缺陷之一。

### P1-02：Timer 的生命周期归属没有真正做到 JS 的调用方自动管理

生命周期语义差异

涉及：`extensions/timer/timer.go`

JS Timer 的核心特征是：

> Timer 创建时自动归属于调用它的 Fiber。

例如：

```ts
ctx.interval(callback, 1000)
```

当调用者退出，定时器自动停止。

Go 当前是：

```go
svc.Interval(callback, duration)
```

它归属于 Timer Service，而不是调用它的 Consumer Fiber。

虽然提供了：

```go
timer.Owned(ctx, trigger, stop)
```

以及 `DebounceHandle`、`ThrottleHandle`，但这要求调用者主动绑定生命周期。

问题更明显的是：

* `Timeout()` 返回的 `Handle.Stop()` 只有 bool 返回值。

* `Interval()` 返回的 `Handle.Stop()` 同样只有 bool。

* `Owned()` 接收 `func() error`。

* 普通 `Debounce()` 和 `Throttle()` 直接丢弃停止句柄。

更重要的是，即使自行包装 `Handle.Stop()`，它也不保证等待已经运行的 Timeout/Interval 回调结束。

所以不能简单说 Timer 已经等价。

建议：

不要让应用开发者每次都记得调用 `Owned()`。

优先提供 Context 绑定接口，例如：

```go
timer.TimeoutOwned(ctx, fn, duration)
timer.IntervalOwned(ctx, fn, duration)
timer.DebounceOwned(ctx, fn, duration)
timer.ThrottleOwned(ctx, fn, duration)
```

统一要求：

* 创建即绑定消费者 Fiber。

* 消费者 Unwind 时禁止新回调进入。

* 等待已经进入的回调结束。

* 回调不能通过停止自身造成自等待。

* Fiber Gone 后不存在遗留回调。

另一个已知问题是 Debounce/Throttle 的 `stop` 在自己的回调中调用会自等待。文档已经承认这一点，但接口层还没有解决。

这项属于真实的 JS 生命周期能力差异。

### P1-03：HTTP SOCKS 代理清理会破坏其他组件的配置

组合语义缺陷

涉及：

* `extensions/http/http.go`

* `extensions/http-socks/component.go`

当前 SOCKS Component 的 Effect inverse 是：

```go
return func() error {
    return svc.SetProxy("")
}, nil
```

这会产生一个问题。

假设：

```text
组件 A：设置代理 A
组件 B：设置代理 B
```

随后 B 退出：

```text
B 的 inverse → SetProxy("")
```

结果是代理 A 也被清除。

这违反了可组合扩展的基本要求：撤销一个组件的贡献，不应破坏其他组件仍然拥有的贡献。

建议：

代理配置应该使用有身份的注册机制，而不是简单覆盖一个全局字符串。

例如：

```text
Proxy Registration
  ├── ID A → Proxy A
  └── ID B → Proxy B
```

撤销 B，只撤销 B 的注册。

最终代理策略可以明确采用：

* 优先级。

* 最近注册者优先。

* 或显式唯一 Provider。

不要依靠简单的 `SetProxy("")` 恢复状态。

另外，当前 SOCKS4/4a 只是生成 URL，并没有真正实现对应拨号能力。这一点文档已经披露，因此不能算完整的 JS 等价实现。

### P1-04：FS 本地 Watch 不支持 JS 的目录递归监听语义

确定的能力缺失

涉及：`extensions/fs/fs.go`

当前 Local Provider 的 Watch：

```go
watcher.Add(filepath.Dir(rp))
```

并且只接受：

```go
filepath.Clean(ev.Name) == rp
```

这意味着它监听的是目标路径所在的父目录，并且只接受目标本身发生的变化。

例如监听：

```text
file:///app
```

期望得到：

```text
/app/a.txt
/app/css/style.css
/app/js/app.js
```

的变化。

但当前实现无法提供这样的递归监听。

JS FS Watcher 的能力包括：

* 目录下的变化通知。

* Watch Filter。

* Ready 事件。

* Error 事件。

* Mount 路由切换时由新 Provider 接管。

Go 目前的 Local Watch 还没有覆盖这些语义。

还有一个问题：Local Watch 对 `watcher.Errors` 只是读取并丢弃，没有将错误反馈给调用者。

建议：

把 Watcher 设计成独立的服务抽象：

```text
Watcher
  ├── Change
  ├── Ready
  ├── Error
  └── Dispose
```

Provider 负责底层监听，FS Service 负责路由和接管，调用者负责监听事件。

不要直接把 fsnotify 的单个文件事件当成 JS Watcher 的等价实现。

### P1-05：Local Provider 持有的 os.Root 没有关闭接口

涉及：`extensions/fs/fs.go`

`NewLocalProvider()` 调用了：

```go
os.OpenRoot(abs)
```

得到一个长期持有的 `*os.Root`。

但是当前 `Provider` 接口没有 `Close()`，Local Provider 也没有公开关闭方法。

这意味着创建 Local Provider 后，根目录句柄没有明确的释放责任。

尤其在长期运行的工业应用里，反复创建、卸载 Provider 会带来资源管理问题。

建议：

增加明确的 Provider 生命周期协议。

可以采用标准 `io.Closer`：

```go
type Provider interface {
    ...
    io.Closer
}
```

但 Memory Provider 的 Close 可以是无操作。

FS Service 在 Provider 所有权明确时负责释放，不能在 Unmount 时无条件关闭一个可能被多个 Mount 共享的 Provider。

需要区分：

* Mount 所有权。

* Provider 实例所有权。

* Watcher 所有权。

### P1-06：HTTP Service 关闭时没有等待正在执行的请求

涉及：`extensions/http/http.go`

当前 `Close()` 关闭所有 Transport 的空闲连接：

```go
tr.CloseIdleConnections()
```

但是这不会等待仍在执行的请求结束。

而 `Do()` 没有维护活动请求计数，也没有统一的 Service 生命周期取消上下文。

可能发生：

```text
HTTP 请求开始
    ↓
HTTP Component 退出
    ↓
Service.Close()
    ↓
Fiber Gone
    ↓
HTTP 请求仍然执行
```

这与文档中强调的资源生命周期完整性不一致。

需要注意，这不意味着所有 HTTP 请求都必须在 Service 退出时强行中断。正确的设计应当明确：

* 是否停止接收新请求。

* 是否取消正在执行的请求。

* 是否允许优雅等待。

* 超时后如何强制关闭。

* Fiber Gone 的保证边界是什么。

建议采用类似 HTTP Server 的 Shutdown 机制：先停止新请求，再等待活动请求，最后执行超时取消。

另外，当前 HTTP 客户端把响应 Body 全部 `io.ReadAll` 到内存，JS HTTP 支持 Stream Response。这是另一项能力差异，不能用于大文件、流式数据等场景时仍宣称等价。

### P1-07：Package Manager 的原子性承诺不成立

涉及：`extensions/package-manager/package_manager.go`

当前 `Apply()` 使用 `go mod edit` 修改 go.mod，失败时：

```go
restore := func() {
    _ = os.WriteFile(path, original, mode)
}
```

这里有两个问题：

* 恢复操作不是原子文件替换。

* 恢复失败被忽略。

如果发生磁盘写入错误，调用者可能得到修改失败的结果，但文件已经处于部分修改状态。

另外：

* `Apply()` 使用 mutex。

* `Report()` 不使用相同 mutex。

所以同一 Service 内并发 `Report()` 与 `Apply()`，可能读到中间状态。

还有一个逻辑问题：同一个批次重复修改同一个 Module 时，`versions` 没有同步更新，返回的 Added/Updated/Removed 和 Details 可能与最终 go.mod 不一致。

建议：

* 先对整个 Change 批次做规范化，拒绝或合并重复模块。

* 使用 `golang.org/x/mod/modfile` 处理 go.mod，而不是维护自己的文本解析器。

* 在临时文件中完成全部修改。

* 验证修改结果。

* 使用原子替换提交。

* Report 与 Apply 共享一致的读写同步策略。

* 恢复失败必须返回给调用方。

另外，当前 Agent 只检测 Go Toolchain，不是 JS Package Manager 那种 npm/pnpm/yarn Agent。这个差异应该明确记录。

### 三、JS 能力等价性审查

这一部分比具体 Bug 更重要，因为它决定了前面文档中的“已实现”是否准确。

### 3.1 Core

| 功能                   | Go 当前情况                    | 等价判断 | 实际问题              |
| -------------------- | -------------------------- | ---- | ----------------- |
| Component / Fiber    | 完整运行时模型                    |      | API 不同，核心语义有对应    |
| 生命周期调和               | Orchestrator / Reconcile   |      | Go 有独立决策域         |
| Dependency Injection | 类型化 Key                    |      | 不需要 JS Proxy      |
| Isolation            | Per-key Realm              |      | 应继续保持             |
| Interception         | MetaKey / Derived Context  |      | 应继续保持             |
| Effect               | install/inverse + Iterator |      | 语法形式不同            |
| Revision             | 退役再插入                      |      | 不复制 JS Fiber 身份保留 |
| Event 注册             | Handle / Once / Effect     |      | 并发执行边界不同          |
| Event Dispatch       | 五种模式                       |      | Bail 的语义不同        |

### Event 的问题值得单独强调

当前 Go 的 `Bail()` 是：

> 按顺序执行，遇到第一个错误就停止。

而 JS Cordis 的 `bail()` 是：

> 按顺序执行，遇到第一个非 undefined 返回值就停止。

这是两个不同的功能。

Go 的 `Bail()` 不能提供 JS 的结果短路能力。

不能因为名字一样就写成已实现。

我建议二选一：

* 实现真正的泛型结果短路 `Bail`。

* 将现有行为命名为 `FailFast`，明确接受差异。

考虑到你要求 JS 能力全覆盖，我倾向于第一种。

另外，`Parallel` 的 Handler 移除行为具有调度依赖性。这是 Go 并发环境下需要接受的差异，但应把边界写入正式契约，而不是只放在实现注释里。

### FS：不能把 Watch 和 ReadFile 等同于完整 FS

JS FS 最新 API 的范围明显比当前 Go FS 更大。

JS FS 的主要操作面

Open / Stream Read

Range Read

Write

Stat / Lstat

ReadDir

Mkdir

Rename

Remove

Copy

Access

Symlink Metadata

Recursive Watch

Watch Filter

Ready / Error Events

URL Resolution

Go FS 当前主要覆盖

OpenReadFileWriteFileStatReadDirRemoveWatchLocal ProviderMemory ProviderMount Routing

Go FS 当前并非没有价值，而是还没有达到 JS FS 的完整操作和观察模型。

我建议 FS 不要继续零散增加函数，而是先建立一份完整的 Provider 接口契约，再让 Local、Memory 两个 Provider 通过同一套 conformance tests。

这也是最成熟的方案：接口定义一次，所有 Provider 共用行为测试。

### Env：当前实现不是完整 dotenv-expand

JS Env 的主要语义：

* `.env`

* `.env.local`

* `.env.{mode}`

* `.env.{mode}.local`

* `NODE_ENV` 决定 mode

* dotenv 解析

* dotenv-expand 变量展开

* process 环境变量覆盖文件变量

* Populate 可逆

Go 已经覆盖了其中很多部分，但还有差距：

* Mode 需要手动传入，没有自动采用 `NODE_ENV`。

* 变量展开目前是一次替换，不是完整的递归展开。

* 没有覆盖所有 dotenv 语法，例如多行引号内容和 `$VAR` 形式。

* `Populate` 在多个 Env Component 同时修改同一个进程变量时，没有完整的多实例所有权协调。

尤其是第四项值得注意。

例如：

```text
Env A Populate: X=A
Env B Populate: X=B
```

如果 A 先退出，B 后退出，当前基于值比较的恢复策略可能留下 A 的旧值。

这是资源恢复的组合问题，不是单纯的 dotenv 解析问题。

### HTTP：不是简单地有一个 net/http 就等价

JS HTTP 的功能范围包括：

* Fetch 风格接口。

* GET / POST / PUT / PATCH / DELETE。

* Request Config。

* Base URL。

* 参数处理。

* Header 合并。

* Response Decoder。

* Stream Response。

* 请求拦截。

* Proxy Agent。

* WebSocket。

* 文件和 Data URL 支持。

Go 当前是一个基于 `net/http` 的简化客户端，接口是 `Do/Get/Post`，并将 Body 完整读取到内存。

它作为 Go 原生 HTTP Service 是有价值的，但不能说 JS HTTP 已经全覆盖。

### 四、CLI 与脚手架的其他问题

### 4.1 Windows 命令行路径转义

涉及：`extensions/cli/cli.go`

当前 `tokenize()` 把反斜杠统一视为转义字符。

这对 Windows 路径尤其不友好。

例如：

```text
C:\Program Files\App
```

反斜杠会被消耗，路径可能变成：

```text
C:Program Files\App
```

这会导致 Windows 用户输入路径时遇到问题。

JS CLI 的解析器与 Go 当前实现并不完全相同。

建议：

不要用一个简单的反斜杠规则处理所有输入。

应明确区分：

* Windows 路径。

* 引号转义。

* Unix 路径。

* Shell 参数输入。

* 纯命令文本输入。

最好将 Tokenizer 作为独立包，做跨平台测试。

### 4.2 Create Cordis 没有真正保证目标目录为空

涉及：`cmd/create-cordis/create.go`

注释说：

> 只写入空目标目录。

但实际 `Generate()` 没有先验证目录为空。

它只是对每个生成文件使用 `O_EXCL`。

因此已有其他文件的目录仍可能被部分填充。

另外，失败回滚只删除已创建文件，没有清理创建的空目录。

还有一点：当前测试验证了生成代码语法，但没有完整验证生成项目可以完成：

```text
go mod tidy
go build
go run
```

建议：

* 明确是否允许向已有项目目录生成。

* 如果只允许空目录，应在开始写入前验证。

* 记录创建的目录并在失败时清理。

* 增加完整生成项目构建测试。

### 五、架构层面的判断

这一轮我反而认为，Kernel 的问题没有新增扩展那么严重。

### 5.1 Kernel 与 Extension 边界总体保持得不错

我检查了以下关键实现：

* `runtime/runtime.go`

* `runtime/fiber.go`

* `runtime/context.go`

* `runtime/orchestrator.go`

* `runtime/reconcile.go`

* `runtime/providers.go`

* `runtime/event_registry.go`

目前主要方向仍然正确：

Kernel

Fiber / Context / Effect / Realm / Dependency / Orchestrator / Revision

继续冻结语义边界

Extensions

Event / FS / Env / Timer / HTTP / Server / CLI / Package Manager / Loader / HMR

扩展能力放在这里是正确的

Applications

通过声明、依赖、Effect 和 Service 组合应用能力

我没有发现这次为了增加 HTTP、FS、CLI 而把它们直接塞进 Kernel 的明显架构倒退。

这是好事。

但是有一个边界问题需要关注：

Extension 内部可以管理资源，但不能形成与 Kernel 相冲突的生命周期语义。

例如：

* Timer 可以管理内部计时器，但不能让消费者退出后仍然运行其回调。

* FS 可以管理 Watcher，但 Watcher 必须能随 Fiber 退出。

* HTTP 可以管理 Transport，但关闭服务时必须明确活动请求的退出语义。

* Server 可以管理 Listener，但必须保证 Fiber Gone 后监听器不再存在。

换句话说，Extension 可以有自己的资源管理器，但不能成为第二个 Fiber 生命周期管理器。

### 5.2 一个建议：统一 Extension Service 的生命周期规范

现在不同扩展对资源的处理方式略有分散。

我建议制定一份短小的规范：

| 规范项        | 要求                   |
| ---------- | -------------------- |
| Service 创建 | 由 Component 激活时创建    |
| Service 提供 | 使用 typed Key         |
| 资源注册       | 必须有明确逆操作             |
| 用户回调       | 不允许持有内部锁执行           |
| 资源停止       | 停止新任务进入              |
| 活动任务       | 明确取消或等待策略            |
| 资源释放       | 必须能够确定性完成            |
| Fiber Gone | 不得存在仍归属该 Fiber 的活动资源 |

不需要再设计新的生命周期框架。

只需要让现有 Extension 逐一满足这份契约。

### 六、文档与验收结论存在的问题

### 八、最终产品方向建议

我建议停止追求“功能目录看起来和 JS 一样”，转而追求：

论文语义完整 + JS 能力覆盖 + Go 原生工程质量。

三个目标要分别验收。

| 目标      | 评价标准                          |
| ------- | ----------------------------- |
| 论文语义    | Definition、操作、状态变化、可逆性和组合性质正确 |
| JS 能力覆盖 | 每个公开功能都有等价实现或明确接受差异           |
| Go 工程质量 | 类型安全、并发安全、资源归属、错误处理、可测试       |

其中有一个原则必须坚持：

论文与 JS 冲突时，论文优先；API 形状不同不算缺失，但行为能力缺失不能算等价。

本轮新增的 FS、Env、HTTP、Server、CLI 等能力，方向本身是正确的。它们让 GoCordis 从一个偏理论的 Runtime，逐渐变成能够承载实际应用的框架。

但现在不应该继续扩张。
